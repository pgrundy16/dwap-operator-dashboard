# Shared booking data contract

## Status of this contract

This contract records the **intended test environment** and the mappings visible in supplied source and workbook exports. It is not a claim that the active Google Sheets have identical settings or current data. The booking columns below were verified against `Booking Requests.xlsx` and the supplied booking Apps Script. `BookingForm.tsx` builds the payload, `bookingApi.ts` invokes a Supabase Edge Function named `booking`, and that function forwards to the booking Apps Script. The `Jobs` headers in the export match the dashboard Apps Script's canonical fields. The labour layout comes from `Labour_Allocations_TimeTicket_Ready (1).xlsx` and the Time Ticket script; the Google Sheet copy still needs verification.

## Identity rules

| Identifier | Purpose | Rule |
| --- | --- | --- |
| `requestId` | Cross-system key for one booking | Generated by booking Apps Script as a UUID per POST; nonempty, unique, immutable, and preserved through edits/retries in the target design. Booking column Y. Never derive it from row position, date, customer name, or phone. |
| `jobId` | Human-readable display/reference | Separate from Request ID. Assign once and persist in `Jobs`; it may use service/date text but must not be recomputed on every read. Not a cross-system join key. |
| Time Ticket `jobKey` | Allocation row key | For a booked job, `booking:` plus the exact Request ID. Manual work uses a `manual:` key and must not be silently merged with a booking. |
| `calendarEventId` | Calendar event pointer | Stored in `Jobs`; retain it when confirming or editing to avoid duplicate events. |

**Current-code caveat:** the dashboard falls back from a missing Request ID to Job ID, and can generate `jobId` from date plus a six-character Request ID prefix. The Time Ticket code can fall back to a booking row number when Request ID is absent. Those fallbacks are compatibility behavior, **not** the target contract. Reject or quarantine missing/duplicate Request IDs before production integration.

## Dashboard operator updates (`Jobs` tab)

The dashboard Apps Script creates `Jobs` if absent and writes the canonical header row below. It merges `Jobs` over booking rows using Request ID, with Job ID as a fallback. These are the **code's canonical field names**, not yet a verified existing Sheet layout.

| Group | Fields | Meaning |
| --- | --- | --- |
| Identity/state | `jobId`, `requestId`, `status`, `calendarEventId` | Display ID, join key, lifecycle state, Jobs calendar pointer |
| Booking snapshot | `serviceType`, `customerName`, `phone`, `email`, `preferredDate`, `preferredTime`, `estimatedTimeHours`, `helpersNeeded`, `pickupAddress`, `dropoffAddress`, `stairsInvolved`, `elevatorAtPickup`, `elevatorAtDropoff`, `submittedAt`, `additionalNotes`, `serviceDetails` | Fields copied/merged from intake; avoid duplicating source truth where possible |
| Quote/payment metadata | `quoteTotal`, `depositAmount`, `balanceDue`, `depositLink`, `depositSentAt`, `depositPaid` | Operator-entered amounts/link and a claimed flag; Square remains payment authority |
| Completion/operations | `confirmedAt`, `completedAt`, `actualDurationHours`, `operatorNotes`, `archiveOn`, `riskFlags` | Operator actions and display metadata |

`quoteTotal`, `depositAmount`, `balanceDue`, and duration fields are numeric in the dashboard contract. Blank numeric cells normalize to `null`. The booking script writes `Estimated Time` as a display string such as `2h`, which the dashboard's number parser does not accept; move and junk payloads currently omit `estimatedDurationMinutes` entirely. `serviceDetails` and `riskFlags` are serialized JSON in the operator sheet. The current script interprets Boolean-like values such as `true`, `yes`, and `1` as true. The `Jobs` sheet should have at most one row per Request ID; duplicate handling needs explicit validation in the test flow.

## Labour allocation workbook

The local prepared workbook has `Monthly Summary`, `Pay Period Time Tracker`, `Time Ticket Log`, `Time Ticket Audit`, and `Time Ticket Config`. Keep actual employee names, rates, customer records, and email addresses out of this repository. In the prepared layout:

| Tab | Structural contract |
| --- | --- |
| `Monthly Summary` | Worker-by-revenue-stream summary; the local template has stream headings in B:I and total hours in J. Check the copied Sheet's formulas and source ranges. |
| `Pay Period Time Tracker` | Pay-period start/end in C3:D3; worker allocation headers on row 8; job rows 10–53; B = work date, C = project/customer, AM (column 39) = Time Ticket job key; worker hours go into the column named by the config's allocation header. |
| `Time Ticket Log` | Raw entry log: Entry ID, Day ID, Employee ID/Name, Work Date, Job Key, Booking Request ID, project, start/end, exact and rounded duration, submission status, timestamps, and sync source. |
| `Time Ticket Audit` | Audit trail for time-entry and day-submission actions. |
| `Time Ticket Config` | Employee-to-allocation-column mapping and setting names; the local file specifies booking Sheet name, column numbers, pay-period range, rounding, time zone, and office email slots. Values containing private data are intentionally omitted here. |

The Time Ticket script rounds **each job** up to the next 15-minute payroll interval by default, while retaining exact minutes in `Time Ticket Log`. The local workbook alone does not prove the Google Sheet copy's formulas, named ranges, or protected ranges are identical.

## Dates, times, and currency

| Field | Contract | Current-code behavior / check |
| --- | --- | --- |
| `preferredDate`, Time Ticket `date`, pay-period work date | Calendar date `YYYY-MM-DD` in `America/Toronto` | BookingForm builds a date string; the export mostly stores actual spreadsheet date cells in B. Dashboard Apps Script formats Sheet dates in the spreadsheet time zone, then script time zone, then `America/Toronto`; Time Ticket defaults to `America/Toronto`. Confirm imported test Sheet time zones. |
| `preferredTime`, start/end | Local 24-hour `HH:mm` | BookingForm sends a time string; the export mostly stores spreadsheet time cells in C. Dashboard normalizes date-like values to `HH:mm`; Time Ticket expects `H:mm` or `HH:mm` and does not support an overnight span in one entry. |
| `submittedAt`, `depositSentAt`, `confirmedAt`, `completedAt`, `archiveOn` | ISO 8601 timestamp with offset/UTC (`Z` preferred) | Dashboard writes ISO UTC timestamps. The browser should format using the business time zone rather than relying on device time zone. |
| Quote, deposit, balance | CAD currency amounts, nonnegative decimal | Current dashboard stores JS numbers and derives balance when blank. Square is the financial source of truth. |

**Known time-zone gap:** the dashboard browser calculates “confirmed today” using UTC date, while Apps Script uses Sheet/script time zone. Near midnight these may differ from Toronto business date. The copied environment should test this before live use.

## Test-copy acceptance checks

1. Compare exact `Sheet1` and `Jobs` headers, blank/duplicate Request IDs, and one synthetic website submission with the tables above.
2. Test retry behavior. The supplied Apps Script generates a new UUID on every POST, and the supplied Supabase Edge Function has no idempotency key or durable deduplication.
3. Confirm dates/times as typed values versus strings, and read the spreadsheet, Apps Script, and calendar time zones.
4. Compare copied labour tabs, formulas, row limits, column AM, config setting names, and employee column lookup with this document.
5. Confirm one synthetic Request ID survives booking → dashboard → Time Ticket → allocation and that no real customer/employee data appears in test fixtures or Git.
